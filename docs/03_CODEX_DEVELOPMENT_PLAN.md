# Книгоскоп — план разработки в Codex

Версия 1.0. Обязательные источники требований: `01_TECHNICAL_REQUIREMENTS.md` и `02_SYSTEM_ARCHITECTURE.md`.

## 1. Общие правила для Codex
1. Перед каждой задачей прочитать все три документа, проверить актуальный код и кратко описать план изменений.
2. Выполнять **одну фазу за раз**, не создавать весь проект одним запросом. После фазы остановиться, показать изменённые файлы, команды запуска, результаты тестов и нерешённые вопросы.
3. Код, имена файлов, таблиц, переменных и API — английские; документация, сообщения пользовательского интерфейса — русские (предусмотреть локализацию).
4. Не хардкодить ключи, пароли, цены, лимиты и адреса провайдеров. Использовать `.env.example` и административные настройки.
5. Каждую миграцию БД и endpoint сопровождать тестами. Не изменять существующие контракты без обновления документации.
6. Не выполнять несанкционированный веб-скрейпинг и не обходить DRM/paywall. Для тестов — фикстуры с разрешёнными текстами.
7. Не заявлять о пройденных тестах без их реального выполнения; фиксировать ограничения среды.
8. При архитектурной неоднозначности предложить вариант и получить подтверждение, если выбор существенно меняет требования.
9. Каждая фаза завершается небольшим проверяемым коммитом (если Git доступен и пользователь разрешил).

## 2. Фазы разработки

### Фаза 0. Каркас репозитория и dev-окружение
**Задача:** создать монорепозиторий `backend/frontend/infra/docs`, README, `.env.example`, Docker Compose для PostgreSQL/Redis/API/frontend/worker, healthcheck и команды запуска. Настроить линтеры, форматирование, pytest/Vitest и CI-скрипты локально.
**Приёмка:** `docker compose config` проходит; API `/health` отвечает; frontend открывается; ключи не нужны; команды тестов задокументированы.

### Фаза 1. База данных и аутентификация
**Задача:** модели users/auth_tokens, Alembic, регистрация/подтверждение email, вход/выход, восстановление пароля, admin CLI, роли и блокировки. Для dev — тестовый почтовый backend.
**Приёмка:** тесты позитивных/негативных сценариев, токены одноразовые, неавторизованный доступ закрыт, созданный администратор входит в `/admin`.

### Фаза 2. Библиотека и импорт
**Задача:** works/editions/text_versions/library_items/folders; TXT/PDF(text layer)/EPUB/DOCX/FB2; безопасный парсинг, дедупликация, личные папки/избранное/сортировка, удаление связи.
**Приёмка:** импорт 5 форматов на фикстурах, один публичный текст для двух пользователей, приватный файл недоступен другому, корректное удаление личной записи.

### Фаза 3. Поиск и источники
**Задача:** `SourceConnector`, поиск сначала локально, затем по конфигурируемым разрешённым источникам; интерфейс выбора точного издания; хранение правового статуса и источника. Интернет-поиск — только выдача кандидатов, скачивание после проверки прав.
**Приёмка:** совпадающие названия различаются по автору/редакции; запрещённый источник не импортируется; внешние ошибки не ломают локальный поиск.

### Фаза 4. Структура текста и читалка
**Задача:** нормализация, дерево разделов и точные диапазоны; двухпанельный интерфейс, мобильные вкладки, fullscreen, темы/шрифты/интервалы, сохранение прогресса.
**Приёмка:** переход к диапазону корректен после перезагрузки; нет ссылок на чужую версию; смартфон и клавиатурная навигация работают.

### Фаза 5. Очередь и AI-инфраструктура
**Задача:** jobs, Celery, provider adapters, секреты, маршруты primary/fallback, тест соединения, классификация ошибок, retries, квоты и учёт usage. Создать mock LLM для локальных тестов.
**Приёмка:** без API-ключей система стартует; мок-задача выполняется в фоне; fallback срабатывает на техническом сбое; квоты не допускают лишний запуск; ключ не виден в ответах/логах.

### Фаза 6. Резюмирование и проверка
**Задача:** обработка чанков, три уровня резюме, дерево глав/эпизодов, ссылки на текст, второй проверочный проход, версия результата, перегенерация главы. В админке — промпты по задачам, переменные, версии, тестирование и откат.
**Приёмка:** для демо-книги генерируются все уровни; ссылки попадают в правильные диапазоны; невалидный диапазон отклоняется; результат и проверка имеют версию модели/промпта.

### Фаза 7. TTS, плеер и караоке
**Задача:** TTSProvider, генерация по запросу, кэш, voice selection, прогресс, скорость, таймкоды слов и fallback к предложениям, автопрокрутка, переход по фразе.
**Приёмка:** тестовый аудиоманифест с известными метками синхронизируется при 1× и 1.5×; перемотка меняет подсветку; повторная генерация с теми же параметрами использует кэш; приватное аудио защищено.

### Фаза 8. Полная админ-панель и статистика
**Задача:** провайдеры, модели, маршруты, промпты, пользователи, лимиты, источники, задачи, ошибки, usage/cost, аудит. Раздел `/admin` с серверной проверкой прав.
**Приёмка:** пользователь не получает админские данные через UI и API; настройки применяются без деплоя; статистика учитывает вызовы; журналы не содержат ключей/текстов.

### Фаза 9. Безопасность, эксплуатация и деплой
**Задача:** rate limits, CSRF/ACL/SSRF тесты, обработка ошибок, backup/restore, Caddy HTTPS, миграции, healthchecks, наблюдаемость, установка на Ubuntu 24.04. Документировать первичный запуск и обновление.
**Приёмка:** сквозной сценарий на staging, восстановление из бэкапа, отсутствие секретов в Git, запуск без AI-ключей, успешные проверки доступа между пользователями.

### Фаза 10. Финальная приёмка
**Задача:** e2e-сценарии: регистрация → поиск/импорт → личная библиотека → обработка → резюме/оригинал → аудио/караоке → удаление. Проверить адаптивность и UX ошибок.
**Приёмка:** все 11 критериев из раздела 5 ТЗ подтверждены тестами или явным протоколом ручной проверки; нерешённые ограничения перечислены.

Запусти доступные проверки. В конце покажи: что сделано, какие файлы изменены,
результаты тестов, команды запуска, известные ограничения и критерии приёмки.

## 5. Перед публичным запуском
Обязательно выбрать и проверить правовой режим источников, политику персональных данных и хранения, SMTP, домен, провайдеров AI/TTS и бюджеты. Эти решения нельзя подменять выдуманными значениями в коде.
